# DOM Snapshot & Action Primitives for a No-CDP Content-Script Follower

_Research date: 2026-09-03. All claims below are from reading actual current source at a cloned commit (paths + hashes given) or a fetched URL — nothing here is from training-data memory of these projects, which move fast and have all materially changed in 2025-2026._

## Answer-first summary

1. **Every "AI browser agent" that ships a real product today (browser-use, Stagehand, chrome-devtools-mcp, Skyvern, playwright-mcp) has converged on CDP** (`Accessibility.getFullAXTree` + `DOM.getDocument`/`DOMSnapshot.captureSnapshot`) for the snapshot, and on CDP `Input.*` for actions. None of them is a working example of a pure content-script, no-CDP agent at production quality — the closest is **nanobrowser's `buildDomTree.js`** (pure content script, no CDP, for the *snapshot* only), but nanobrowser's *actions* (click/type) go through `chrome.debugger` + Puppeteer CDP as the primary path, falling back to untrusted DOM events only on failure. This is direct precedent for R-13's escalation model, not a counterexample to it.
2. **The only production-quality, spec-faithful role/name-from-raw-DOM algorithm that needs zero CDP and zero flags is Playwright's injected `ariaSnapshot.ts`/`roleUtils.ts`** — a hand-written reimplementation of the ARIA role-computation and AccName algorithms, running as ordinary page JS. This is the one piece of all five investigated projects that is directly portable, wholesale, into a content script. Its `[ref=eNN]`-style YAML output is the cleanest LLM-facing format found in this survey.
3. **`element.computedRole`/`computedName` (the "just ask the browser for the accessible role" API) is NOT shipped** — it has sat "in developer trial (behind a flag)" since Chrome 41 (2015) and a Chromium accessibility engineer said in April 2026 it "should have been removed a long time ago." A content script must reimplement AccName in JS (as Playwright does); there is no shortcut.
4. **Closed shadow roots are not fully a dead end for an extension**: page JS can never see inside a closed shadow root, but the genuine Chrome extension API **`chrome.dom.openOrClosedShadowRoot(element)`** (shipped, unflagged, since Chrome 88) can, and Stagehand's own extension code uses exactly this API for shadow-root traversal without CDP. Verified independently against `developer.chrome.com` in this session (not just the subagent's claim) — see §4.
5. **Untrusted (`isTrusted:false`) events are functionally complete for click/select/scroll and, with the native-setter bypass, for React/Vue-controlled text inputs** — but real sites do check `event.isTrusted` specifically against extensions, so it is a genuine, unspoofable detectability tell, exactly matching what I-01/I-02 already flag.
6. **Contenteditable and file inputs both have a working untrusted path with real caveats**: `execCommand('insertText', …)` is deprecated but still the only way to mutate contenteditable content with correct `inputType` without OS-level keys (a manually-dispatched bare `InputEvent` does **nothing** to the DOM — confirmed by Playwright's own fallback code doing the mutation by hand before firing the event for notification only); file inputs *can* be set via `new DataTransfer()` + `input.files = dt.files` entirely untrusted, but only for **in-memory** files (no real disk path, no native picker) — CDP's `DOM.setFileInputFiles` remains the only way to attach a real filesystem-backed file.
7. **Real character typing is impossible without CDP, full stop.** Untrusted `KeyboardEvent`s fire listeners but insert no characters — confirmed architecturally: Playwright's entire `Keyboard` class has no DOM-dispatch code path at all, it is 100% `Input.dispatchKeyEvent`/`Input.insertText`. This matches what I-01 already states as known.
8. **Viewport culling, occlusion checking, and interactivity filtering are all doable in a content script with standard DOM APIs** (`checkVisibility()`, `getBoundingClientRect`, `elementFromPoint`, `getComputedStyle`) — browser-use's, nanobrowser's, and Skyvern's heuristics for "is this interactive" are portable almost verbatim; only their CDP-only signals (native `isClickable`, full paint-order/stacking-context resolution, DevTools-only `getEventListeners()`) have no content-script equivalent and must be approximated or dropped.
9. **Stable cross-step element identity** is solved by every project the same way in spirit: a per-snapshot id (index/uid/ref) cached against a durable node-identity key (browser-use: `backendNodeId`; Stagehand/chrome-devtools-mcp: `backendNodeId`/`loaderId`; Playwright: an expando `_ariaRef` cached directly on the element). For no-CDP, the durable key must be our own: a `WeakMap<Element, id>` for same-render-cycle stability plus an xpath/stable-attribute-hash fallback for cross-reload correlation — never a DOM-attribute stamp, which would be a detectable mutation under R-02.
10. **Set-of-marks (visual overlay) is dead in practice, confirming C-05.** Skyvern's own hint-marker/bounding-box overlay code is present but explicitly marked deprecated/dead in its current source; nanobrowser's highlight overlay is real and **on by default** (a genuine R-02 anti-pattern to avoid — ours must default off/opt-in and use no DOM mutation for indexing).

## 1. browser-use — now CDP-first end-to-end, no JS DOM walker at all

Commit `5b50d1f511189c9df93e7f0bcb9da943b2d5780b` (2026-09-03), `github.com/browser-use/browser-use`. There is **no `.js` file anywhere under `browser_use/dom/`** — the historic `buildDomTree.js`/`index.js` JS walker is gone; the whole pipeline is Python driving `cdp_use`'s typed CDP client (`browser_use/dom/service.py:6-9`).

- **Fetch**: three concurrent CDP calls per frame — `DOM.getDocument({depth:-1, pierce:True})` (shadow DOM + iframes come free, closed shadow roots included since CDP pierces them), `DOMSnapshot.captureSnapshot({computedStyles, includePaintOrder:True, includeDOMRects:True})` (gives a native `isClickable` boolean and pre-resolved paint order/z-stacking, no live style/layout queries needed), and `Accessibility.getFullAXTree({frameId})` per frame, merged by `backendNodeId` (`service.py:588-635`).
- **Visibility**: `is_element_visible_according_to_all_parents` (`service.py:250-343`) reads `display`/`visibility`/`opacity` off the pre-captured snapshot (no live `getComputedStyle`) and culls by a `viewport_threshold` param (default **1000px** expansion; `None` disables culling — `service.py:64,294`).
- **Interactivity**: `browser_use/dom/serializer/clickable_elements.py`, `ClickableElementDetector.is_interactive` — ordered checks: JS-click-listener flag (from a `Runtime.evaluate({includeCommandLineAPI:true})` call to DevTools' `getEventListeners()`, CDP-only), tag/attribute allowlists, AX-node property scan (`focusable`/`editable`/`expanded`/`pressed`), interactive-role set, then a `cursor:pointer` fallback sourced from the snapshot's computed style.
- **Occlusion**: `browser_use/dom/serializer/paint_order.py` — a rectangle-union algorithm consuming CDP's `paintOrders` array to resolve full CSS stacking-context occlusion, something a content script would have to reimplement from scratch to match.
- **Index assignment**: indices are **`backendNodeId` values reused directly**, with a synthetic-counter fallback only on collision (`serializer.py:648-658`) — confirmed by `tests/ci/browser/test_dom_selector_index_collisions.py:80-87` (`[5]<input.../>` vs `[101]<input.../>`).
- **Format**: `[index]<tag attr=val .../>` per line, tab-indented, with `*` prefix for newly-appeared elements, `|scroll element[idx]|`, `|IFRAME|`/`|FRAME|`, `|SHADOW(open)|`/`|SHADOW(closed)|` markers — confirmed literally in `tests/ci/test_image_only_dom_representation.py`.
- **Cross-origin iframes**: recurse via a separate CDP `Target.attachToTarget` into the iframe's own `frameTargetId` (`service.py:975-1073`) — **disabled by default** (constructor flag `cross_origin_iframes=False`), and fundamentally not portable to a content script (no way to reach across an OOPIF boundary without CDP).

**Transfers to no-CDP**: the serialization format itself; the tag/attribute/role/class interactivity heuristics; CSS-visibility filtering (replicate with `getComputedStyle`); the viewport-threshold math (pure `getBoundingClientRect` arithmetic); open-shadow traversal; same-origin iframe traversal (this is exactly what the pre-CDP `buildDomTree.js` era did).
**Does not transfer**: full AX tree, native `isClickable`, native paint-order/occlusion, cross-origin iframe targets, closed-shadow piercing via CDP, DevTools-only `getEventListeners()`, `backendNodeId` identity itself.

## 2. Stagehand — a second MV3 extension, but one that requires the browser to already expose CDP

Commit `50146e426baff4e6507c6302dbee50ee0c9bc6bc` (2026-09-03), `github.com/browserbase/stagehand`. Now a two-package monorepo: `packages/sdk-ts` (Node client) drives an installed **MV3 extension**, `packages/extension` (`@browserbasehq/stagehand-extension`), whose service worker opens its own raw `WebSocket` straight to the browser's `/json/version` CDP endpoint (`packages/extension/understudy/browserWebSocketTransport.ts:64-69`). **This only works because the browser was already launched with remote-debugging exposed** (Playwright/Puppeteer-launched, or Browserbase cloud browsers) — it is categorically unavailable to a normal store-installed extension in an end user's ordinary Chrome profile, which is exactly our situation.

- **AX fetch**: `Accessibility.getFullAXTree` per frame (`packages/extension/understudy/a11y/snapshot/a11yTree.ts:15-40`), mapped to xpaths via a **separate, parallel** pure-DOM xpath-building walk (`domTree.ts:154-215`) that also explicitly walks `node.shadowRoots` from `DOM.getDocument({pierce:true})`.
- **Format**: `[<encodedId>] <role>: <name> [selected] [checked]`, 2-space indented, with per-iframe outlines spliced inline (`treeFormatUtils.ts`) — `encodedId = frameOrdinal-backendNodeId`.
- **Shadow-root piercing without CDP, for the xpath-resolution side**: `packages/extension/dom/locatorScripts/shadowRoots.ts:1-16` calls **`chrome.dom.openOrClosedShadowRoot(element)`**, falling back to `element.shadowRoot` for open roots — this is the notable finding for us (see §4; independently re-verified against `developer.chrome.com`).
- **Actions**: real CDP `Input.dispatchMouseEvent`/`dispatchKeyEvent`/`insertText` (`packages/extension/understudy/page.ts:1527-1994`) — trusted, OS-level synthetic input, not in-page `dispatchEvent`.

**Transfers to no-CDP**: the absolute-xpath builder (`packages/extension/dom/a11yScripts/index.ts:26-67`, pure `parentNode`/`shadowRoot.host` walk); the hand-rolled shadow-piercing XPath parser/evaluator (`dom/locatorScripts/xpathResolver.ts`); `chrome.dom.openOrClosedShadowRoot()` itself; the outline serialization format and pruning heuristics (`isStructural`, `removeRedundantStaticTextChildren`).
**Does not transfer**: `Accessibility.getFullAXTree`, `backendNodeId`-keyed identity, trusted `Input.*` actions, and the extension's own CDP-bootstrap mechanism (`Extensions.loadUnpacked` / self-connect to the browser's debug endpoint).

## 3. Nanobrowser, Skyvern, Magnitude, chrome-devtools-mcp, Playwright ariaSnapshot/playwright-mcp

### Nanobrowser (original) — the closest real precedent, and instructive about what "no-CDP" actually costs

Commit `24a14b76e14a9c30fd84878ca7985049d1e7d064`, `github.com/nanobrowser/nanobrowser`. `chrome-extension/public/buildDomTree.js` (1505 lines) **is** a pure content script, no CDP, injected via `chrome.scripting.executeScript` — this is the one real precedent for exactly our snapshot problem.

- Manual recursive walker over `childNodes` (not `TreeWalker`), `WeakSet` cycle guard, `MAX_DEPTH=100`, results flattened into a `DOM_HASH_MAP` keyed by incrementing string ids (an id-graph, not nested JSON) — lines 1238-1495.
- `isElementVisible`: `offsetWidth>0 && offsetHeight>0 && visibility!=='hidden' && display!=='none'` (lines 525-530) — a plain-JS analog of `checkVisibility()`.
- `isTopElement` (occlusion): `document.elementFromPoint()`/`shadowRoot.elementFromPoint()` at rect center + corners, walking up `parentElement` from the hit result (lines 790-885) — exactly the `elementFromPoint` occlusion-check technique from §4, already proven in a shipping content script.
- `isInteractiveElement` (lines 541-782): computed `cursor` in an interactive-cursor whitelist short-circuits true first (comment: "Genius fix"); then tag whitelist + `disabled`/`readonly`; contenteditable; class/`aria-haspopup` heuristics; interactive ARIA-role whitelist; last resort `window.getEventListeners` (DevTools-only, degrades to an `onclick`-attribute check in a plain content script).
- **Viewport culling**: `args.viewportExpansion` (default `0`; `-1` disables all culling) — same shape as browser-use's `viewport_threshold`, done with plain `getBoundingClientRect` math (lines 894-933).
- **Shadow DOM**: open roots only, via `node.shadowRoot` (lines 1464-1470); hit-testing inside a shadow tree correctly re-scopes to `shadowRoot.elementFromPoint()` via `getRootNode()` (lines 836-853).
- **Iframes**: same-origin recursion via `contentDocument`, offset-tracked for highlight-box placement; cross-origin access throws and is caught, node marked `error`, no recovery attempted (lines 1406-1447) — no `all_frames`-based cross-frame injection is used here.
- **Highlight overlay — an R-02 anti-pattern to avoid**: `doHighlightElements` is hardcoded `true` (always builds/injects a `#playwright-highlight-container` with colored boxes + numeric labels into `document.body`); only *visibility* is gated by `showHighlightElements`, which is wired to the user setting `displayHighlights`, **default `true`** (`packages/storage/lib/settings/generalSettings.ts:13,32`). I.e. nanobrowser's overlay is opt-out, not opt-in — the opposite of what R-02 requires.
- **Actions — the key finding**: nanobrowser's manifest declares the `debugger` permission and connects via `puppeteer-core`'s `ExtensionTransport` (`chrome-extension/src/background/browser/page.ts:1-9`) — i.e. **clicks and typing are done over real CDP** (`element.click()`/`element.type(text,{delay:50})` through Puppeteer, which itself issues `Input.dispatchMouseEvent`/`dispatchKeyEvent`), and only fall back to untrusted `el.click()` / plain `Event('input')`/`Event('change')` dispatch when the CDP path fails (`page.ts:1285-1330, 1101-1188`). **Nanobrowser is not a working no-CDP action example — it is a working example of exactly the R-13 escalation model** (CDP-backed trusted input as the standing mode here, not an escalation, but architecturally the same mechanism I-01 is asking about).

### Skyvern

Commit `8abdfa95c56e3e06cdc210be7887aabd633550c6`, `github.com/Skyvern-AI/skyvern`. `skyvern/webeye/scraper/domUtils.js` (3733 lines) is a portable, injectable content script with heavy `isInteractable()` heuristics (~225 lines, handles Angular/Kendo/DataTables widget special cases) — but the surrounding Python orchestration is Playwright/raw-CDP (multiple "engine" backends). Notably, its visual **hint-marker/bounding-box set-of-marks overlay code is still in the file but explicitly marked deprecated** (`domUtils.js:2731-2745,2976-2985`, source comment: "no longer rendered during scraping... scheduled for removal") — Skyvern has converged from visual set-of-marks onto DOM-text-tree serialization, the same direction as everyone else, confirming C-05's framing that marks are optional/secondary.

### Magnitude — excluded from the comparison (product pivoted)

Commit `fc61fecdf079e3291e4d8ac0e2fcd6d52218ed91`, `github.com/magnitudedev/magnitude` (not `magnitudelabs`/`magnitude-run`, both 404). As of 2026-09-01 this repo is a **local-LLM-inference-server / coding-agent plugin product** — no Playwright/Puppeteer dependency, no click/screenshot code anywhere in `packages/agent|harness|sdk`. Its `packages/dom-extract` package is a static HTML→Markdown extractor (cheerio-based, modeled on Python's `unstructured`), not a live interactive-element indexer. **Magnitude should not be cited as a current vision/set-of-marks browser-agent reference** — its historical architecture is not verifiable from current source.

### chrome-devtools-mcp — official Google MCP server, fully CDP-based

Commit `401a1192b6e745a360c2a011a4bb69a67bf2af7a`, `github.com/ChromeDevTools/chrome-devtools-mcp`. `take_snapshot` (`src/tools/snapshot.ts:9-46`) calls Puppeteer's `page.accessibility.snapshot({includeIframes:true, interestingOnly:!verbose})` (`src/TextSnapshot.ts:56-59`) — i.e. CDP `Accessibility.getFullAXTree` under the hood. **uid scheme**: `` `${snapshotId}_${counter}` `` cached against `` `${loaderId}_${backendNodeId}` `` so the same uid persists across repeated snapshots of an unchanged node (`src/TextSnapshot.ts:70-101`). **Format**: `uid=3_17 button "Submit" focusable` (role, quoted name, boolean AX properties) — `src/formatters/SnapshotFormatter.ts:36-104`. **Resolution**: `getElementByUid` looks up the uid in a live `Map`, calls Puppeteer's `node.elementHandle()` (→ CDP `DOM.resolveNode` on the cached `backendNodeId`) — `src/McpPage.ts:639-664`. Actions go through `handle.asLocator().click()` — real CDP input. Nothing here is content-script-portable except the *shape* of the uid-caching idea (stable id keyed to a durable node identity, pruned when absent from the latest snapshot).

### Playwright `ariaSnapshot` + playwright-mcp refs — the one directly-portable, gold-standard piece

Playwright commit `2b7a5f2ea1cea04b549c5378498c1b16b6bc6a6f`; playwright-mcp commit `8a13ef8e9f7385a0f89477922127f31cbfde9761` (now folded into the main Playwright monorepo, `packages/playwright-core/src/tools/backend/*`). Files: `packages/injected/src/ariaSnapshot.ts` (549 lines), `packages/injected/src/roleUtils.ts` (1360 lines), `packages/isomorphic/ariaSnapshot.ts` + `ariaSnapshotRenderer.ts`.

- **Role/name computation is pure DOM/JS, no CDP, no browser AX API at all** — `roleUtils.ts:281-300` (`computeAriaRole`): explicit `role` attribute → implicit role via a tag-name lookup table (`kImplicitRoleByTagName`) → ARIA "presentation inheritance" conflict resolution walking ancestors, all with inline WAI-ARIA 1.2 spec citations. Accessible-name computation (`computeAccessibleNameComposite`, line 517+) reimplements the W3C AccName algorithm from scratch (label/labelledby/content-based naming). **This is the load-bearing artifact for our project**: a real, currently-shipping, spec-faithful role/name-from-raw-DOM implementation that any content script can adapt wholesale.
- **Format**: YAML list, `- button "Submit" [ref=e12] [cursor=pointer] [box=x,y,w,h]`, 2-space indent per depth (`ariaSnapshotRenderer.ts:26-124`). This is the cleanest LLM-facing shape found across all six projects surveyed.
- **Ref generation**: a module-level counter (`let lastRef=0`) whose value is cached directly as an expando property on the element itself (`element._ariaRef`, `packages/injected/src/ariaSnapshot.ts:218-232`) and **reused across snapshots** as long as role+name are unchanged — no `WeakMap` needed since the property lives on the node. In `'ai'` mode, refs are only assigned to elements that are visible **and** `receivesPointerEvents` — i.e. the interactivity filter is applied at ref-assignment time, not as a separate pass. Cross-frame refs get an `f<N>` prefix.
- **Resolution**: a custom `aria-ref=` Playwright selector engine (`injectedScript.ts:245,737-741`) looks the ref up in `_lastAriaSnapshotForQuery` (the info map from the most recent snapshot only) and checks `element.isConnected` before returning it — stale refs from an old snapshot correctly resolve to nothing.
- **playwright-mcp's `browser_click`**: if the `target` string matches `/^(f\d+)?e\d+$/` it's routed through `aria-ref=`; otherwise treated as a CSS selector/described locator (`packages/playwright-core/src/tools/backend/tab.ts:492-517`). Clicks are then real `Locator.click()` — CDP-backed, trusted.

**Transfers to no-CDP, wholesale**: `roleUtils.ts`'s role/name algorithm, the YAML-with-`[ref=eNN]` format, the expando-cached-ref identity scheme, the visible+`receivesPointerEvents` filter-at-assignment-time pattern.
**Does not transfer**: the `aria-ref=` selector engine's dependency on Playwright's own selector-engine registration machinery (trivially reimplementable as a plain lookup function), and the trusted `Locator.click()` action itself.

## 4. Content-script techniques available without CDP (verified against 2026 sources)

| API | Status (Sept 2026) | Key fact | Source |
|---|---|---|---|
| `element.checkVisibility()` | **Shipped, stable**, Chrome 105+, Baseline 2024 | Options: `contentVisibilityAuto`, `opacityProperty`, `visibilityProperty`. Does **not** catch out-of-viewport, occluded, or (per MDN) reliably zero-size elements — quoted: "may still return `true`" for elements outside the viewport or occluded | developer.mozilla.org/.../Element/checkVisibility |
| `getBoundingClientRect()` + iframe offsets | Shipped, universal | Rect is relative to the containing document's own viewport; cross-frame parent-relative coordinates require manually summing each ancestor iframe's own rect. Not explicit on MDN's page — standard practitioner knowledge, flagged as such | developer.mozilla.org/.../getBoundingClientRect |
| `IntersectionObserver` | Shipped, universal | Scoped to one document/frame tree — cannot observe a target in a different frame's document; complements, doesn't replace, per-frame rect math | developer.mozilla.org/.../IntersectionObserver |
| `document.elementFromPoint`/`elementsFromPoint` | Shipped, Baseline (~2020) | Coordinates are always frame-local; calling from the parent over a cross-origin iframe returns the `<iframe>` element itself, never its content | developer.mozilla.org/.../elementFromPoint |
| `element.computedRole`/`computedName` (AOM) | **NOT shipped** — behind a flag since Chrome 41 (2015) | chromestatus feature 5530552681627648: "In developer trial (Behind a flag)". A Chromium a11y engineer, April 2026: "It was only ever experimental; it probably should have been removed a long time ago." A replacement proposal (`element.implicitAria`) is being discussed instead of ever shipping this | api.chromestatus.com/api/v0/features/5530552681627648; github.com/w3c/aria/issues/2663 |
| AccName-in-JS reimplementation | **The realistic, production-proven fallback** | W3C AccName 1.2 Working Draft actively maintained (published 2026-08-27); Playwright's `roleUtils.ts` is a real, current, shipping example of exactly this | w3.org/TR/accname-1.2/; Playwright source (§3 above) |
| Closed shadow roots — **page JS** | Impossible, no workaround | `element.shadowRoot` is `null` for closed roots by spec; `getRootNode({composed:true})` reveals only that a shadow root exists, not its content | developer.mozilla.org/.../Element/shadowRoot |
| Closed shadow roots — **extension API** | **Possible** — `chrome.dom.openOrClosedShadowRoot(element)`, shipped since Chrome 88, no permission listed | "Gets the open shadow root or the closed shadow root hosted by the specified element." Used in production by Stagehand's extension for exactly this purpose (§2). Independently re-verified against `developer.chrome.com` in this session — no explicit statement found of isolated-world-content-script availability vs. other extension contexts; verify empirically before relying on it | developer.chrome.com/docs/extensions/reference/api/dom; `packages/extension/dom/locatorScripts/shadowRoots.ts:1-16` (Stagehand) |
| `content_scripts.all_frames: true` | Shipped, standard MV3 | Injects an independent copy of the content script into every matching frame, including cross-origin ones (subject to `host_permissions`), matched per-frame independently. Cross-origin content is handled by that frame's own script instance relaying results up via `chrome.runtime.sendMessage`/`postMessage` — never by reaching across the origin boundary from the parent frame's script | developer.mozilla.org/.../content_scripts |
| `MutationObserver` | Shipped, universal since 2015 | Standard invalidation signal for a stale element-index map — observe `{childList:true, subtree:true, attributes:true}`, debounce, re-scan | developer.mozilla.org/.../MutationObserver |

## 5. Acting on the chosen element without CDP

| Action primitive | Works untrusted? | Technique | Caveats |
|---|---|---|---|
| Click | Yes | `el.click()` or full `pointerdown→mousedown→pointerup→mouseup→click` dispatch with bbox-center coordinates | `event.isTrusted` is always `false` and unforgeable; a real, current source (dev.to/js_bits_bill) shows sites checking `isTrusted` **specifically against browser extensions** — this is the one deterministic, unspoofable tell |
| Text input (React/Vue controlled) | Yes | Native **prototype** value setter — `Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype,'value').set.call(el, value)` — then `dispatchEvent(new Event('input',{bubbles:true}))`/`change` | Plain `el.value=x` is swallowed by React's instance-level value tracker; this is `dom-testing-library`'s `setNativeValue` (`src/events.js:104-123`, commit `e395d5b8`), tracing to `facebook/react#10135` |
| Contenteditable | Partially | `document.execCommand('insertText', false, text)` — deprecated but functional, the only way to get real mutation + correct `inputType` without OS-level keys | A bare `dispatchEvent(new InputEvent('input',...))` does **nothing** to the DOM — confirmed by Playwright's own `bidiInsertText.ts` (`packages/injected/src/bidiInsertText.ts:43-63`), which does the mutation by hand via `Range`/`Selection` and fires the `InputEvent` only afterward, purely as a notification for rich-text editors |
| `<select>` | Yes | `select.value = x`; dispatch `input` + `change` | No native-setter bypass needed — both nanobrowser (`page.ts:1004-1005`) and Playwright (`injectedScript.ts:858-861`) do plain assignment |
| File input | Partially | `new DataTransfer()`, `dt.items.add(file)`, `input.files = dt.files`, dispatch `input`+`change` — confirmed as real, current, **untrusted-JS** production code in Playwright's own `injectedScript.ts:973-994` | Only produces an **in-memory** `File` — no real disk path, no native picker, no directory upload. CDP `DOM.setFileInputFiles` remains required for a filesystem-backed file; this is a genuine, narrow escalation case for R-13/I-02 |
| Scroll into view | Yes | `el.scrollIntoView({block:'center', inline:'nearest'})` | Ordinary trusted-safe API, no gating |
| Keyboard typing | **No** | N/A | Confirmed architecturally: Playwright's entire `Keyboard` class has zero DOM-dispatch code paths — 100% CDP `Input.dispatchKeyEvent`/`Input.insertText`. Matches I-01's existing "known" statement exactly |

**Nanobrowser's real click/type implementation** (the only shipping no-CDP-*capable* extension in this survey) actually uses `chrome.debugger` + `puppeteer-core`'s `ExtensionTransport` as its primary path (`page.ts:1285-1330,1101-1188`) and only falls back to untrusted `.click()`/`Event()` dispatch on failure — i.e. it is architecturally identical to what R-13's escalation toggle already describes, not a counterexample to needing it.

## 6. Stable element references across steps

Every project solves this with the same shape: **a per-snapshot id, cached against a durable node-identity key, invalidated when the key disappears.**

| Project | Per-snapshot id | Durable key | Cache location |
|---|---|---|---|
| browser-use | `backendNodeId` (reused directly) | `backendNodeId` | CDP-native, no cache needed |
| Stagehand | `frameOrdinal-backendNodeId` | same | CDP-native |
| chrome-devtools-mcp | `snapshotId_counter` | `` `${loaderId}_${backendNodeId}` `` | `Map` on the `McpPage` instance, pruned each snapshot |
| Playwright ariaSnapshot | `e<N>` / `f<N>e<M>` | (role, name) at assignment time | **expando property directly on the element** (`element._ariaRef`) |
| browser-use's replay layer | — | `stable_hash` (dynamic-class-filtered) + xpath + `ax_name` | `DOMInteractedElement` (`views.py:982-1047`), used across page reloads where `backendNodeId` doesn't survive |

**Recommendation for our no-CDP case**: a `WeakMap<Element, id>` in the content script for same-render-cycle stability (no DOM mutation — satisfies R-02's "avoid detectable DOM mutations"), with a **stable hash** (tag + role + accessible name + a denylist-filtered attribute set, following browser-use's `stable_hash` pattern of stripping dynamic/generated classes) plus xpath as the cross-reload/re-render correlation key when the `WeakMap` entry is gone (element replaced by a re-render, not just moved). Never stamp a `data-*` id onto the page — Playwright's expando-property trick (`element._ariaRef`) is the right middle ground: invisible to `querySelectorAll`/CSS/most fingerprinting, but still an own-property a sufficiently paranoid site could enumerate via `Object.getOwnPropertyNames` — the `WeakMap` is strictly stealthier and should be preferred.

## Recommendation

**Snapshot format** — a flat, indexed text list, closest to browser-use's `[idx]<tag ...>` crossed with Playwright's `[ref=...]`/`[box=...]` fields (needed for R-08's pixel-mode correlation):

```
[12] button "Add to cart" bbox=140,860,96,36
[13] input[type=email] name=email value="" bbox=140,760,320,32
     placeholder="you@example.com"
[14] a "View cart (3)" href=/cart bbox=980,24,64,24
*[15] select "Size" value="M" bbox=140,700,120,32
  [16] option "S" selected=false
  [17] option "M" selected=true
|SHADOW(open)|[18] input[type=text] role=combobox bbox=200,300,240,32
|IFRAME same-origin| (12 elements below, prefixed)
  [19] button "Confirm" bbox=... (frame-relative, offset-accumulated)
```

- **Index**: assigned by a `WeakMap<Element,int>` counter at snapshot time, not a DOM attribute — no detectable mutation (R-02). `*` prefix for elements not present in the previous snapshot (cheap diff via the WeakMap's membership).
- **Fields per line**: role/tag, accessible name (AccName-in-JS, following Playwright's `roleUtils.ts` algorithm — not `computedRole`/`computedName`, which are unshipped), current `value` for form controls, `href` for links, and `bbox=x,y,w,h` (viewport-relative, offset-accumulated across same-origin iframe boundaries) so the Follower can correlate a DOM index with a screenshot region in `both` mode per R-08.
- **Filtering rules** (all must hold, adapted from browser-use/nanobrowser's heuristics minus their CDP-only signals): (1) `checkVisibility({opacityProperty:true, visibilityProperty:true})` is true, size > 0; (2) within viewport ± a configurable threshold (nanobrowser/browser-use default ~0-1000px; recommend ~200px for token economy, `-1`/`Infinity` to disable for full-page scans); (3) is the top-hit element at its bbox center via `elementFromPoint` (occlusion check, frame-local coordinates inside iframes); (4) interactive per: tag allowlist (`button,input,select,textarea,a,details,summary,option`) OR explicit/implicit ARIA role in an interactive-role set OR `getComputedStyle(el).cursor==='pointer'` OR has an inline `onclick`/`role` attribute (drop the DevTools-only `getEventListeners()` check — no content-script equivalent, framework-attached listeners will simply be under-detected, a known, acceptable gap); (5) not `aria-hidden="true"` and not inside a `display:none` ancestor.
- **Shadow DOM**: open roots traversed via `element.shadowRoot`; attempt `chrome.dom.openOrClosedShadowRoot(element)` for closed roots and fall back to "opaque, unlisted" if it throws or is unavailable in the isolated world (verify empirically — flagged as unconfirmed in §4).
- **Iframes**: same-origin traversed inline via `contentDocument` with rect-offset accumulation; cross-origin handled via `all_frames:true` + `chrome.runtime.sendMessage` aggregation into the same background/side-panel-owned snapshot, each subtree tagged with its frame id.
- **Action primitives** (mapped to §5): `click` (pointer-event sequence, bbox-center coords, `el.click()` fallback), `type` (native-setter + `input`/`change` for inputs/textareas; `execCommand('insertText')` for contenteditable), `select` (`.value` + `change`/`input`), `scrollIntoView({block:'center'})`, `uploadFile` (in-memory `DataTransfer` only — document the real-path limitation as an R-13 escalation case), and an explicit **not-supported** primitive for real keystroke typing / real-file-path upload, routed to the R-13 CDP-escalation toggle rather than faked.
- **Token estimate** (reasoned, not independently benchmarked — no source in this survey published a measured count): each line runs roughly 8-20 tokens (index + role/tag + a name truncated to ~40 chars + one or two optional value/href fields + a 4-integer bbox). A typical content page after filtering yields on the order of 30-80 interactive elements (a form-heavy or nav-heavy page can run 100-200+). That puts a typical DOM-mode snapshot at **roughly 500-2,000 tokens**, with the `bbox=` field adding on the order of 150-500 tokens across a full snapshot for `both`-mode pixel correlation. Recommend measuring this empirically against real target pages once the serializer exists, rather than treating this estimate as load-bearing.

## Risks

- **`chrome.dom.openOrClosedShadowRoot` availability in an isolated-world content script is unconfirmed by documentation** — verified it exists and is unflagged (Chrome 88+), and Stagehand's extension code calls it from what appears to be content-script-adjacent code, but neither `developer.chrome.com` nor this research explicitly confirms isolated-world (vs. background/service-worker-only) availability or any permission requirement. Spike this before depending on it for closed-shadow coverage.
- **Losing browser-use's/Skyvern's DevTools-only `getEventListeners()` signal** means framework-attached click handlers on otherwise-unstyled `<div>`s will be under-detected relative to CDP-based competitors — expect some real interactive elements to be missed on JS-framework-heavy pages (React/Vue apps with custom-styled clickable divs) unless the cursor/role/attribute heuristics catch them.
- **Occlusion/paint-order approximation**: `elementFromPoint`-based occlusion (what nanobrowser does) is cheaper but weaker than CDP's native paint-order resolution (what browser-use does) — multi-point sampling (center + corners, as nanobrowser does) mitigates but does not eliminate false positives/negatives on complex stacking contexts.
- **Cross-origin iframe aggregation adds real latency and complexity** (message round-trips per frame) compared to CDP's single recursive call — budget for this in the snapshot-build time, especially on pages with many ad/widget iframes.
- **The R-13 tension is real and already correctly scoped by I-01**: nanobrowser's own reference implementation resolves it by using CDP as the *standing* mode, not an escalation — if our low-observability requirement (R-02) forces untrusted-events-as-standing-mode, expect measurably worse success rates on sites with `isTrusted` checks or React-controlled inputs that don't respond to the native-setter bypass, and no working path at all for real character-by-character typing or real-file uploads without the escalation.
