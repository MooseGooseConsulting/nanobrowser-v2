# Object store and handle-based tooling (research, 2026-10-12)

Question: every "object" is a string today (`artifact.save {content: string}`, screenshots as data URLs, 36k-char userscript results and 60k-char snapshots pasted into prompts). What should a proper object store look like?

## Findings

### 1. Binary storage in an MV3 service worker
- IndexedDB and Cache Storage work in the extension service worker; Local/Session Storage do not. All extension contexts (SW, pages, side panel, offscreen) share one origin's storage. https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies
- OPFS: `navigator.storage.getDirectory()` is available in Web Workers; `createSyncAccessHandle()` is Dedicated-Worker-only. In an extension SW, `createWritable()`/`getFile()` work and `createSyncAccessHandle` throws "not a function". https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle , https://stackoverflow.com/questions/74769974/use-opfs-origin-private-file-system-inside-chromes-extension-service-worker
- A 2026 extension guide shows the SW pattern `dir.getFileHandle(name,{create:true}).createWritable()` then `file.getFile().slice(a,b)` for lazy slice reads. https://mv3-extension.com/core-apis-cross-browser-data-management/chrome-storage-api-sync/storing-large-blobs-and-files-in-an-extension/ (secondary source)
- Quota/eviction: Chrome docs say `unlimitedStorage` "affects both extension and web storage APIs and exempts extensions from both quota restrictions and eviction"; `navigator.storage.persist()` is the alternative (same docs URL as above). A Chrome engineer confirmed the mechanism (unlimited extensions are treated as durable) and that OPFS sits in the default bucket, but one developer in that thread reports OPFS being wiped despite the permission. https://groups.google.com/a/chromium.org/g/chromium-extensions/c/EfAXciu90yY ; tracking issue https://github.com/w3c/webextensions/issues/388
- Performance: no authoritative benchmark found for 100-500 KB blobs. One blog measured 500 x ~200 KB blob inserts into IndexedDB at ~2.4 s in Chrome 121 (about 5 ms each). https://lucioduran.com/blog/browser-storage-apis-opfs-indexeddb-sqlite-wasm . The OPFS speed claims in the literature are for sync access handles in workers, which an SW cannot use. At tens of screenshots per run either store is fast enough; measure before optimising.

### 2. Getting bytes out
- Native messaging: JSON, UTF-8, 32-bit length prefix; host->extension max 1 MB, extension->host max 64 MiB. https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging . The repo already enforces both (`host/src/framing.ts`). There is no binary framing, so base64 is the practical encoding (+33%). A 500 KB JPEG is a ~670 KB message: one message, no chunking. Chunk only above ~40 MiB.
- Alternative to base64: a localhost HTTP server started by the host, with the SW doing `fetch(PUT, body: Blob)`. Works (pattern in https://github.com/guest271314/native-messaging-file-writer ) but adds a port, auth and lifecycle surface. Not worth it at screenshot sizes.
- The SW has no `URL.createObjectURL`; use `data:` URLs or an offscreen document with reason `BLOBS`. https://developer.chrome.com/docs/extensions/reference/api/offscreen , https://stackoverflow.com/questions/73348151/downloading-a-large-blob-to-local-file-in-manifestv3-service-worker . A Chromium-group answer says data URIs must be under ~64 MB; a StackOverflow report says very long `data:` URLs were silently truncated by `chrome.downloads.download`. Unresolved; test our size. https://groups.google.com/a/chromium.org/g/chromium-extensions/c/u0NH7L3v9L4
- `chrome.runtime.sendMessage` cannot carry Blob/ArrayBuffer in Chrome (JSON-style serialisation); use `postMessage`/MessageChannel to an offscreen doc. https://github.com/w3c/webextensions/issues/293

### 3. Handles in other agents
- browser-use: `FileSystem` with `todo.md`, `results.md`, and `extracted_content_N.md`. Large extraction goes to a numbered file and only a pointer stays in memory. `describe()` shows files under ~600 chars whole, else 200 chars head + "... N more lines ..." + 200 chars tail. The system prompt says: "If the file is too large, you are only given a preview... Use `read_file`". `ActionResult.include_extracted_content_only_once` shows content to the model for one step only. https://github.com/browser-use/browser-use/blob/058e1cf7/browser_use/filesystem/file_system.py , https://github.com/browser-use/browser-use/blob/main/browser_use/agent/views.py
- Playwright MCP: `browser_snapshot {filename}` "Save snapshot to markdown file instead of returning it in the response"; screenshots with no `filename` go to `--output-dir` and are also returned inline unless `--image-responses=omit`; `--snapshot-mode=none` stops auto-attached snapshots; `--output-max-size` evicts old outputs. Known bug: explicit filenames resolve against cwd, not output-dir. https://playwright.dev/mcp/snapshots , https://playwright.dev/mcp/tools/screenshots , https://playwright.dev/mcp/configuration/options , https://github.com/microsoft/playwright-mcp/issues/1731
- Claude Code: tool results over ~25K tokens (and a hard-coded 50K-char layer) are persisted and replaced with `<persisted-output>Output too large (61.3KB). Full output saved to: <path> Preview (first 2KB): ...`; the model reads slices with Read offset/limit. Changelog v2.1.105: format-specific recovery hints (jq for JSON, computed Read chunks for text); v2.1.91: per-tool `_meta["anthropic/maxResultSizeChars"]` up to 500K. https://github.com/anthropics/claude-code/issues/31686 , /47631 , /42869 , https://github.com/anthropics/claude-agent-sdk-python/commit/e94a74d7f4c7858813130ef9d32d3099a417c0bf . Documented failure: a head-only 2 KB preview hid the `id` fields, and the model fabricated them. https://github.com/anthropics/claude-code/issues/45770
- MCP `resource_link` content block: `uri`, `name`, optional `title`, `description`, `mimeType`, `size`. https://github.com/modelcontextprotocol/modelcontextprotocol/pull/603 , https://mcp.mintlify.app/specification/2025-06-18/server/resources . Vendor guidance (weaker source): return a ranged slice with `rangeReturned`/`hasMoreAfter`/`nextRange` so the model does not mistake a prefix for the whole. https://connector.zone/guides/a-file-too-large-to-return-in-one-piece/
- Stagehand: no handle scheme for the model, but its 2026 `TrajectoryRecorder` writes `.trajectories/{runId}/{taskId}/trajectory.json` plus `screenshots/probe/{1..N}.png`, with events keyed by `stepIndex` and `evidenceRole` "agent" or "probe"; its older collector dedups screenshots with MSE then SSIM via sharp. https://github.com/browserbase/stagehand/pull/2131 , https://github.com/browserbase/stagehand/pull/1072

### 4. Screenshots per step
- `captureVisibleTab`: options `{format:'png'|'jpeg', quality:0-100}`; `tabs.MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND = 2` (Chrome 92+). https://developer.chrome.com/docs/extensions/reference/api/tabs ; options per https://www.creativeworksofknowledge.com/en/cwk-quests/chrome-extensions-quest/dom-tools/screenshot-and-clipping/
- Our own `src/page/driver.ts` records `captureVisibleTab` stalling on hidden/busy tabs. The manifest grants `debugger`, but the current trusted tier permits only `Input.*`; implement a separate screenshot path before treating CDP `Page.captureScreenshot {format, quality (jpeg only), clip, optimizeForSpeed}` as an available alternative. https://docs.rs/browser-protocol/latest/browser_protocol/page/struct.CaptureScreenshotParams.html
- Sizes (secondary sources, measure ours): JPEG q80 about 5x smaller than PNG on text pages; JPEG 100-500 KB vs PNG 1-5 MB for 1920-wide pages. https://botcloud.dev/blog/screenshot-best-practices/ . WebP pipelines exist in some MCP servers, but `captureVisibleTab` cannot emit WebP.
- For the model: Anthropic says pre-downscale to fit the image limits, start at 1280x720 (about 80% of the pixel budget), otherwise the API silently downscales and click coordinates drift. https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude (2026-05-13). The reference computer-use loop returns a screenshot after every action. https://github.com/anthropics/anthropic-quickstarts/blob/3347e36f7911f2cd2702108078b0ccbe5189cf7b/computer-use-demo/computer_use_demo/tools/computer.py

## Recommended design

1. **Host disk is the source of truth; the browser store is a staging cache.** Eviction guarantees are contested, so never rely on OPFS alone. Add `unlimitedStorage` anyway.
2. **Browser store: OPFS via `createWritable` in the SW**, one file per object at `objects/<runId>/<id>.<ext>`; the index is a directory listing plus the host manifest. IndexedDB-Blob is an acceptable fallback; the choice is not performance-driven. Nothing here needs an offscreen document.
3. **Handle shown to the model** (shape borrowed from MCP `ResourceLink` and browser-use `describe()`):
   `[obj o_0007 | userscript_result | application/json | 36,412 chars, 812 lines | keys: items[148], page, total | PREVIEW head+tail 400 chars, TRUNCATED: ... | read_object{id,offset,limit} query_object{id,path} view_object{id}]`
   Include a structural summary (keys, array lengths, first/last record id) so a head-cut cannot hide load-bearing fields. Inline anything under ~1.5 KB whole. Slice tools return `range`, `hasMore`, `nextOffset`. Cap the complete serialized slice response below the host->extension 1 MB limit; keep the 256 KiB payload cap as an additional bound and account for JSON escaping, the response envelope, and base64 overhead.
4. **Export**: `object.put {runId,id,mime,sha256,b64}` over native messaging, one message per object (<=40 MiB); the host writes mode 0600 into `artifacts/<runId>/objects/` and appends an index line to the run log. `chrome.downloads` stays for an explicit user "save as", using a `data:` URL.
5. **Screenshots**: JPEG q~75 at <=1280 px wide for telemetry and model. Capture once after each state-changing action once the page settles (well under 2/sec) and once at the end; skip when a cheap perceptual hash of a 32x32 downscale is unchanged. The image goes to the model only on `view_object` or when the run is vision-enabled; otherwise telemetry only. Each is one `object.put` plus a run-log event `{step, tabId, url, objectId, bytes, sha256}`.

## Open questions
- Do the free Nemotron Leader/Follower models accept images at all? If not, screenshots are telemetry-only and `view_object` is moot.
- Largest `data:` URL that `chrome.downloads.download` accepts reliably (sources conflict); test at 1, 8 and 40 MB.
- Does `fetch(dataUrl).then(r => r.blob())` work in the SW (avoids atob cost)? Is OffscreenCanvas available there for hashing and downscaling? Not verified here.
- Switch screenshot capture to CDP (`debugger` already granted) to avoid the hidden-tab stall and the 2/sec cap?
- Retention and cleanup (Playwright has `--output-max-size`); screenshots of logged-in pages cannot be redacted, so rely on 0600 and run-dir cleanup.
- Should `view_object` re-attach once only (browser-use `include_extracted_content_only_once`) or persist in history?
